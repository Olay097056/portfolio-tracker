## Question

ระบบจำอะไรข้ามการประชุม และวัดว่าที่นั่งไหนแม่นยำกว่ากันยังไง?

ต้นฉบับ: *"สมองส่วนกลาง — ความรู้ที่พิสูจน์แล้ว · จำเฉพาะข้อสรุปที่รอดจากการโจมตี ความเชื่อมั่นลดลงตามเวลาและถูกท้าทายซ้ำได้เสมอ"* + *"สถิติความแม่นยำรายที่นั่ง"*

## ทำไมถึงถูกบล็อกโดย ticket 03

ทั้งสองอย่างนี้มีค่าก็ต่อเมื่อการประชุมให้ผลที่ **มีคุณภาพพอจะจำ** — ถ้า ticket 03 พบว่ามติออกมาเป็นคำกว้างๆ การสร้างระบบความจำมาเก็บคำกว้างๆ ก็ไม่มีประโยชน์ ต้องรู้ผลจริงก่อน

## ตัวเลือกที่ต้องตัดสินใจ (ถาม user ทีละข้อ)

### สมองส่วนกลาง
1. **จำอะไร** — เฉพาะข้อสรุปที่ผ่านการพิสูจน์ (ตาม ticket 04) หรือรวมข้อที่ตรวจไม่ได้แต่น่าสนใจด้วย
2. **ความเชื่อมั่นลดตามเวลายังไง** — เชิงเส้น / ครึ่งชีวิต / ตามอายุของข้อมูลที่ใช้พิสูจน์ ต้องเป็นสูตรที่เขียนโค้ดได้ ไม่ใช่ให้ LLM ให้คะแนนเอง
3. **"ถูกท้าทายซ้ำ" หมายถึงอะไรในทางกลไก** — การประชุมครั้งใหม่หยิบความรู้เก่ามาตรวจซ้ำกับข้อมูลปัจจุบันไหม ถ้าขัดกันแล้วยังไง (ลบทิ้ง / ลดความเชื่อมั่น / เก็บทั้งสองเวอร์ชันพร้อมวันที่)
4. **ป้อนกลับเข้าประชุมครั้งถัดไปไหม** — ถ้าใช่ ป้อนเท่าไหร่ (ความรู้สะสมโตขึ้นเรื่อยๆ = โทเคน input โตขึ้นเรื่อยๆ = ค่าใช้จ่ายโตแบบไม่มีเพดาน) **ต้องมีเพดานชัด**
5. **เก็บที่ไหน** — ตาราง SQLite ใหม่ใน `portfolio.db` (pattern เดียวกับ `model_score_history`) หรือแยกไฟล์แบบ `bondcrisis.db` ที่ `country_ai_service` ใช้

### สถิติรายที่นั่ง
6. **วัดจากอะไร** — สัดส่วนข้อกล่าวอ้างที่ผ่านการพิสูจน์ (วัดได้ทันที) หรือความแม่นของจุดยืนรายสินทรัพย์ที่ออกมาถูกทางจริง (ต้องรอผลตลาด — และอันนั้นเป็นงานของแผน `boardroom-signals`)
7. **ที่นั่งมาจากโมเดลเดียวกันหมด** (DeepSeek ล้วน) — สถิติจะบอกอะไรได้จริง? มันวัด "prompt ไหนดีกว่า" ไม่ใช่ "โมเดลไหนเก่งกว่า" — ยอมรับข้อจำกัดนี้แล้วยังทำไหม หรือตัดทิ้ง
8. **cold start** — สถิติยังไม่มีข้อมูลพอในช่วงแรก แสดงอะไร (ต้องไม่โชว์ 1/1 = 100% แบบหลอกตา — บทเรียนเดียวกับ ticket accuracy disclosure ของแผน investor-upgrades)

## Answer

Grilling ครบ 8 ข้อ (2026-08-09) — user ยืนยันทุกข้อ — สูตร decay + state machine ท้าทายซ้ำ + เพดานป้อนกลับ + นิยามสถิติ พร้อมเขียนโค้ดใน ticket 06

### สมองส่วนกลาง
1. **จำอะไร** — เฉพาะข้อสรุปที่**ผ่านการพิสูจน์** (claims verified ที่เข้า `plain.proven` ของมติ) — memory: `statement_md ≤ 200 ตัวอักษร, confidence, tags, source_meeting_id, category` · knowledge: ข้อเท็จจริงภายนอกที่ลงมติรับ (proposal → votes → ceo_adopt) — ความเห็น/ตรวจไม่ได้/partial ไม่เข้าทั้งคู่
2. **สูตร decay (deterministic — ไม่มี LLM/ไม่มี cron):** `conf(t) = conf0 × 0.5^(t/half_life)` · `expires_at = as_of(ข้อมูลที่ใช้พิสูจน์) + TTL หมวด` (ตารางเดียวกับ knowledge stale) — `half_life = TTL/2` · `conf0`: unanimous 85 / contested 70 / partial-ทิศทาง 55 · ฉีดที่ conf ≥ 60 · retired อัตโนมัติที่ < 30
3. **"ถูกท้าทายซ้ำ" ในทางกลไก** — ทุกประชุมเต็ม ฉีด memory/knowledge (conf ≥ 60) เข้าเฟสตรวจสอบ → ผู้ท้าทายตรวจซ้ำกับข้อมูลปัจจุบันด้วยโค้ด: ตรง → reaffirmed (conf +5) · ขัด → challenged (conf ×0.5) · challenged + ตรวจอีกครั้งยังขัด → retired · มีอันใหม่ดีกว่า (knowledge) → superseded (⇄ ลิงก์) — **ไม่ลบทิ้ง** (filter "ปลดระวาง" ดูย้อนหลัง) · challenged ต้อง 2 ครั้งติดต่อกันถึง retired · บันทึก `last_checked_meeting_id`
4. **เพดานป้อนกลับ (คงที่ ไม่โตไม่จำกัด)** — knowledge ≤ **8** (K1..K8 ตามต้นฉบับ) + memory ≤ **10** (conf ≥ 60 เรียง conf) · statement ≤ 200 ตัวอักษร → รวม ~5k tokens input คงที่ · retired/superseded/conf<60 ไม่ฉีด · ฉีดเข้า [ข้อมูลระบบ] ทุกที่นั่ง
5. **เก็บที่** — `portfolio.db` ผ่าน SQLAlchemy (เพิ่มใน database.py) — 7 ตาราง mirror ต้นฉบับ: boardroom_meetings / messages / seats / memory / knowledge / seat_stats / seat_model_stats (ตัด) — schema ตาม ticket 01

### สถิติรายที่นั่ง
6. **วัดจาก** — "claim ผ่านพิสูจน์" = `verified/total` วัดทันทีหลังประชุม (verified/partial/failed แยก — unverifiable เป็นกลาง) · "ทิศทางถูก" (`stances_correct`) เก็บ field ไว้แต่**ค่าจริงเป็นงาน boardroom-signals** (due date → outcome.h.results → win/loss/push) — แสดง "—" จนกว่าจะมีผล
7. **โมเดลเดียวกัน วัด "prompt ไหนดีกว่า"** — ทำต่อ + footnote ตายตัวใน UI: *"ที่นั่งทั้งหมดใช้ DeepSeek ตัวเดียวกัน — สถิติวัดคุณภาพบทบาท/prompt ไม่ใช่ความเก่งของโมเดล"* — จับ prompt พัง (claims_failed สูง) + ที่นั่งเห็นตาม (verified 100% ไม่เคยค้าน) · **ตัด `boardroom_seat_model_stats`** (โมเดลเดียวไม่มีความหมาย)
8. **cold start** — `claims_total < 10` → ไม่แสดง % ("3 ข้อ · รอข้อมูลเพิ่ม") · `10–49` → % + เศษส่วนเสมอ (67% (6/9)) · `≥ 50` → + advisory ได้ (<45% ⚠️) · **ห้ามโชว์ 100% เมื่อ n < 10** · 0 ข้อ → "—"

**ส่งต่อ:** ticket 06 ได้ schema ตารางครบ + สูตร decay + state machine + เพดาน + นิยามสถิติ — ticket 07 ได้ footnote + หน้า memory/knowledge/scoreboard (filter สถานะ + เศษส่วน + minimum sample)

**ห้ามแตะโค้ด production**
