## Question

สองทีมของเราต่างกันตรงไหน แต่ละทีมมีกี่บุคลิก และใครเป็นคนเคาะออเดอร์?

## ข้อเท็จจริงตั้งต้น (ตัดสินแล้ว อย่ารื้อ)

**user ตัดสิน 2026-08-09:**
- ต้นฉบับ 9 ทีม → **ของเรา 2 ทีมพอ**
- "แข่งข้ามค่ายโมเดล" → **แข่งข้ามกลยุทธ์/บุคลิก** เพราะเรามี DeepSeek `deepseek-v4-flash` อย่างเดียว

**ผลที่ตามมาที่ต้องยอมรับและเขียนไว้ใน answer:** สองทีมที่ใช้โมเดลเดียวกันจะ**มีอคติร่วมกัน** — ถ้าไม่ออกแบบให้ต่างกันจริงในระดับกลยุทธ์ ทั้งสองจะเทรดคล้ายกันจนการแข่งขันไม่มีความหมาย นี่คือความเสี่ยงหลักของทั้งแผน และเป็นสิ่งที่ ticket 03 ต้องพิสูจน์ด้วยการรันจริง

**ต้นทุนคือข้อจำกัดหลัก:** 2 ทีม × (หัวหน้า 1 + ลูกทีม 6) = 14 บุคลิก ถ้าทุกคนพูดทุกเทิร์น = 14 คอล/เทิร์น ถ้าเทรดวันละ 4 เทิร์น = 56 คอล/วัน **ก่อนนับ**ห้องประชุมของแผนอื่น

## ตัวเลือกที่ต้องตัดสินใจ (ถาม user ทีละข้อ)

1. **กี่บุคลิกต่อทีม** — ตามต้นฉบับ (หัวหน้า 1 + ลูกทีม 6) หรือลดลง? เสนอตัวเลือกพร้อมต้นทุนต่อเทิร์นให้ user เลือก — ความเห็นตั้งต้น: **เริ่มที่หัวหน้า 1 + ลูกทีม 2** แล้วขยายทีหลังถ้าเห็นว่าคุ้ม
2. **สองทีมต่างกันยังไงให้ต่างจริง** — ต่างที่อะไร: กรอบเวลา (สั้น/ยาว)? ความเสี่ยงที่ยอมรับ? สายเทคนิคอล vs สายมหภาค? สายตามเทรนด์ vs สายสวนทาง? — ต้องต่างในระดับที่ทำให้**ตัดสินใจต่างกันจริงจากข้อมูลชุดเดียวกัน** ไม่ใช่แค่ต่างชื่อ
3. **ใครเคาะออเดอร์** — หัวหน้าทีมตัดสินคนเดียวหลังฟังลูกทีม? โหวต? หรือลูกทีมแต่ละคนเสนอแล้วหัวหน้าเลือก? (กระทบจำนวนคอลโดยตรง)
4. **ลูกทีมเห็นข้อมูลอะไร** — เห็นชุดเดียวกันหมด หรือแบ่งกันดู (แบ่งกัน = มุมต่างจริง แต่เสี่ยงตัดสินจากข้อมูลไม่ครบ)
5. **ทีมเห็นผลของอีกทีมไหม** — ถ้าเห็นจะกลายเป็นลอกกัน ถ้าไม่เห็นก็แข่งกันจริง — ความเห็นตั้งต้น: **ไม่เห็นกัน**
6. **reuse เครื่องยนต์ประชุมจากแผน `boardroom` ไหม** — จากผล ticket 01 ข้อ 3 ถ้า `/trade-desk/meetings` โครงสร้างใกล้เคียงห้องประชุมหลัก การ reuse จะประหยัดมาก แต่ต้องไม่ทำให้เครื่องยนต์บวมจนดูแลยาก — ตัดสินให้ชัดพร้อมเหตุผล
7. **ทีมเทรดตอนไหน** — แอปไม่มี scheduler ตัดสิน: เทรดเฉพาะตอนเปิดแอป / มี background job / ให้ user กดเปิดเทิร์นเอง (ต้นฉบับมีสวิตช์หลัก + โควตาเทิร์น ซึ่งแปลว่าเขามี worker ของเขา)
8. **สวิตช์หลัก** — เอาไหม (ต้นฉบับมี: ปิดแล้วทีมไม่เปิดเทิร์นใหม่ แต่ SL/TP/liq ของไม้เดิมยังทำงาน) — ความเห็นตั้งต้น: **เอา** เพราะเป็นเบรกฉุกเฉินคุมค่าใช้จ่าย

## Answer

Grilling ครบ 8 ข้อ (2026-08-10) — user ยืนยันทุกข้อ — ผัง 2 ทีม + กลไกตัดสินใจ + จังหวะเทรด พร้อมเขียน prompt ใน ticket 03/06

### 1. กี่บุคลิกต่อทีม — **หัวหน้า 1 + ลูกทีม 2** (3 คอล/ทีม/เทิร์น)
ต้นทุน: 6 คอล/เทิร์น (2 ทีม) ≈ $0.003 · 4 เทิร์น/วัน ≈ $0.012/วัน — ถูกกว่าห้องประชุม ~10 เท่า — ขยายทีหลังได้ (เพิ่ม prompt ไม่แก้โครงสร้าง)

### 2. สองทีมต่างกันยังไง — **กลยุทธ์ 2 แกน (อิงบทบาทต้นฉบับ 6 ตัว)**
- **ทีม A สายเทรนด์**: ลูกทีม เทรนด์+เทคนิคอล · กรอบ 1–7 วัน · risk 5–10% · เข้าเมื่อเทรนด์ชัด (ราคา>MA + โมเมนตัม + คะแนนโมเดล)
- **ทีม B สายกลับค่า**: ลูกทีม มหภาค+สวนฝูง · กรอบ 7–30 วัน · risk 2–5% · เข้าเมื่อ extreme (z-score + FRED + ข่าว)
- ต่างที่ฟังก์ชันตัดสินใจ (TEAM_A/B_CONFIG: risk/lookback/entry rule/stop rule) — **พิสูจน์ใน ticket 03** (เทรดเหมือนกัน = ออกแบบยังไม่ต่างพอ)
- **หลักฐานจริง (เปิดหน้า reference ด้วย login user)**: ทีม = ค่ายโมเดลล้วน 9 ค่าย (DeepSeek +8.68% #1 ... Grok -11.86% #9) · โครงสร้าง/บทบาทเหมือนกัน · ต่างที่โมเดล + เป้ารายสัปดาห์ (หัวหน้าตั้ง +1.0–2.0%) · 88 ตลาด (คริปโต 20/40 หุ้น 20/37 MACRO 10 FX 1) · digest อันดับ ≠ pnl (score-based) — เรา 1 โมเดล → ต่างที่กลยุทธ์

### 3. ใครเคาะออเดอร์ — **หัวหน้าเคาะเด็ดขาด** (ลูกทีม 2 เสนอ → หัวหน้าฟัง + เคาะ + directive 📌 ได้)
3 คอล/เทิร์น: ลูกทีม A → ลูกทีม B → หัวหน้า (SL/TP สั่งตอนเปิด — execute ด้วยโค้ด ไม่เสียคอล)

### 4. ลูกทีมเห็นข้อมูลอะไร — **แบ่ง pack ตามสาย · หัวหน้าเห็นครบ**
A: technical pack (ราคา/MA/RSI/volume/คะแนนโมเดล) · B: macro pack (FRED/ข่าว/COT/จุดตรวจ) · หัวหน้าเห็นทั้ง 2 + พอร์ตทีม (รวมมุมแล้วเคาะ — ไม่เสี่ยงข้อมูลไม่ครบ)

### 5. ทีมเห็นผลอีกทีมไหม — **ไม่เห็นกัน** (พอร์ต/ออเดอร์/equity/สรุปของอีกทีม — prompt กรองด้วย build_team_context(team_id)) — UI โชว์ทั้ง 2 ให้คนดูเท่านั้น

### 6. reuse เครื่องยนต์ประชุม boardroom ไหม — **reuse ชั้น LLM (llm_call/token/cost) + ชั้นข้อมูล (build_snapshot + price resolver) · ไม่ reuse กลไก 7 เฟส** — สร้าง `trade_desk_service.py` ใหม่ (เทิร์นลูป 3 คอล + execute + ตารางแยก: trade_teams/trade_positions/trade_orders/trade_snapshots — ห้ามแตะ trading_signals)

### 7. ทีมเทรดตอนไหน — **(ก) Piggyback + ปุ่ม "เปิดเทิร์นเลย"** + แสดง "เทิร์นถัดไป" จริง
- หลังเทิร์นจบ → next_turn_at = now + interval (ทีม A 4 ชม. · ทีม B 12 ชม.) · เปิดหน้า tab → ตรวจ master+โควตา+next_turn_at → รัน (ทีมละ 1 รอบ/เปิด) · ปุ่มกดเร่ง (นับโควตา) · โควตา 4/ทีม/วัน
- ต้นฉบับใช้ worker 24/7 จริง (next_turn_at จองล่วงหน้า ทุกทีม) — **ของเรา piggyback** (ยอมรับ: ไม่เปิดแอป = ไม่เทรด) — **ออกแบบ engine เป็น `run_due_turns()` ฟังก์ชันเดียว → ย้ายขึ้น pg_cron ได้ทีหลังไม่ต้องแก้โค้ด**

### 8. สวิตช์หลัก — **เอา** (เบรกฉุกเฉินคุมค่าใช้จ่าย)
ปิด → ทีมหยุดเทิร์นใหม่ แต่ราคาไหล + SL/TP ไม้เดิมยังทำงาน (ตรงต้นฉบับ tdMasterOff) · สถานะโชว์บนหน้า · โควตาแยกจากสวิตช์

### Backlog เพิ่ม (จาก user — 2026-08-10)
- **แผนย้ายสถาปัตยกรรมไป Vercel+Supabase** (แบบต้นฉบับ) — ได้ worker 24/7 ฟรี (pg_cron + Edge Function) + Auth/RLS · จุดเสี่ยง: data fetching จาก serverless (FRED bot-detect/yfinance rate) ต้องมี proxy/cache · ทางสายกลาง: Supabase local (Postgres + pg_cron) บนเครื่องเดิม — **ทำทีหลัง หลังแผนนี้เสร็จ**
