## Answer (user-approved 2026-08-09 — "ลุยเลย")

Prototype approved as-is: `prototype-07/index.html` (standalone HTML mock, disposable, in `.scratch/forecast-tab/prototype-07/`). Layout decisions locked:

1. **แผงควบคุมตัวแปร** — ฝั่งซ้าย 380px: 5 preset pills บนสุด (น้ำมันช็อก/เฟดช็อก/วิกฤตเครดิต/เงินฝากไหลออก/รีเฟลชัน) → slider จัดกลุ่มตามหมวด 4 กลุ่ม (อัตราดอกเบี้ย / ความผันผวน-สินค้าโภคภัณฑ์ / เครดิต-เงินเฟ้อ / สภาพคล่องธนาคาร) + กลุ่มข่าว 6 slider (ระดับข่าวแรง ต่อโมเดล) → แถวรีเซ็ต + ค่าจริงปัจจุบัน + disclaimer
2. **ผลลัพธ์ 6 โมเดล** — การ์ด ranked (#1-#6 เรียงตาม simulated) แต่ละการ์ด: badge สถานะ (ทำงาน/กำลังก่อตัว/ไม่ทำงาน) + score → simulated + delta สี (เขียว >0.5 / แดง <−0.5 / เทา) + double progress bar (base slate = score%, overlay accent/orange = simulated%) + เส้นขอบประเหลืองเมื่อค่าจำลอง ≠ จริง + ข้อความ ▲ เริ่มพิจารณาสัญญาณ / ▼ ต่ำกว่าเกณฑ์ก่อตัว + expand สินทรัพย์ที่เกี่ยวข้อง + ตาราง factor
3. **การแยกค่าสมมติจากค่าจริง** — เส้นขอบประสีเหลืองบนการ์ดที่มีค่าจำลอง + banner ชัดเจนใต้ header + disclaimer ใต้ปุ่มรีเซ็ต
4. **การแตกดูราย factor** — ใน expand ของแต่ละการ์ด (ตาราง factor: มหภาค/โครงสร้างตลาด/ข่าว/ยืนยัน/บทลงโทษ × ปัจจุบัน/จำลอง/Δ)
5. **สถานะกำลังคำนวณ** — badge ลอยมุมขวาบน "⏳ กำลังคำนวณ..." (debounce 250ms)
6. **preset** — 5 อัน pill บนสุดของแผงซ้าย
7. **มือถือ** — grid ยุบเป็น 1 คอลัมน์ (<900px) slider เต็มความกว้าง

## Question

tab นี้หน้าตาเป็นยังไงจริงๆ เมื่อวางลงในดีไซน์ระบบของแอปเรา?

ต้นฉบับใช้ Tailwind **แอปเราไม่มี Tailwind เลย** — ทุก visual เป็น inline style (ดู `ModelsDashboard.tsx`, `SignalsDashboard.tsx` ที่ใช้ค่าคงที่ `INK` palette) การมิเรอร์จึงเป็นการแปลภาษา ไม่ใช่การก๊อป และมีเรื่องที่ตัดสินบนกระดาษไม่ได้ ต้องเห็นของจริงก่อน

## ทำไมต้อง prototype ไม่ใช่แค่เขียน spec

ปลายทางของแผนที่นี้คือ spec ที่โมเดลอื่นอ่านแล้วทำได้เลย — spec ที่บรรยาย layout ด้วยคำพูดล้วนจะถูกตีความคลาดเสมอ prototype ทำให้ user เห็นแล้วบอกได้ว่า "ไม่ใช่" ก่อนที่ spec จะถูกเขียนผิด

## สิ่งที่ต้องทำ

สร้าง prototype ตาม `/prototype` skill — ของทิ้งได้ ไม่ต้องต่อ backend จริง (ใช้ข้อมูลปลอมในไฟล์ได้) เป้าหมายคือให้ user ตัดสินรูปทรง ไม่ใช่ส่งมอบโค้ด

ต้องเห็นให้ชัดในสิ่งเหล่านี้:

1. **แผงควบคุมตัวแปร** — slider/ช่องกรอกจากผล ticket 03 วางยังไงเมื่อมีหลายตัว จัดกลุ่มตามหมวด (อัตราดอกเบี้ย / ความผันผวน / เครดิต / สภาพคล่องธนาคาร) ไหม เลื่อนหน้าจอยาวแค่ไหน
2. **ผลลัพธ์ 6 โมเดล** — ก่อน/หลัง วางคู่กันยังไง แสดง delta ยังไง อันดับที่เปลี่ยนสื่อยังไง (ลูกศร? ย้ายตำแหน่งจริง?)
3. **การแยกค่าสมมติออกจากค่าจริง** — หลักการห้ามละเมิดของแผนนี้ ทำให้เห็นด้วยตายังไง (สี ป้าย เส้นขอบ พื้นหลัง)
4. **การแตกดูราย factor** — ถ้า ticket 04 ตัดสินให้ API คืน delta ราย factor ต้องมีที่แสดง
5. **สถานะกำลังคำนวณ** — ถ้า ticket 04 เลือก backend round-trip ผู้ใช้เห็นอะไรระหว่างรอ
6. **preset** — ถ้ามีจาก ticket 03 วางตรงไหน
7. **มือถือ** — แอปนี้ใช้บนจอเล็กด้วยไหม slider หลายตัวบนมือถือเป็นปัญหาคลาสสิก
