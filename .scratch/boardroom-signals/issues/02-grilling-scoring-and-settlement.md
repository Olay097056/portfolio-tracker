## Question

จุดยืนหนึ่งอันจะถูกตัดสินว่า "ถูกทาง" ตอนไหน ด้วยเกณฑ์อะไร และใครเป็นคนตัดสิน?

ถ้านิยามนี้หลวม สถิติทั้งหน้าจะไม่มีความหมาย — และแย่กว่านั้นคือมันจะดู**น่าเชื่อถือทั้งที่ไม่มีความหมาย** ซึ่งอันตรายกว่าไม่มีสถิติเลย

## ข้อเท็จจริงตั้งต้น

- แอปไม่มี scheduler — ทุกอย่างคำนวณตอนมีคนเรียก API ถ้าไม่เปิดแอปสามวัน จุดตรวจ +1/+3 วันจะไม่มีใครไปเก็บ ณ เวลานั้น
- `signals_service.compute_stats()` มีสูตรสถิติชุดหนึ่งอยู่แล้วสำหรับ tab "สัญญาณเทรด" (win rate, profit factor, expectancy, max drawdown) — **ดูก่อนว่า reuse ได้แค่ไหน** อย่าเขียนสูตรซ้ำถ้าใช้ของเดิมได้
- บทเรียนที่เพิ่งเจอ (2026-08-09): `compute_stats` เคยคืน `float("inf")` เป็น profit factor แล้วทำให้ทั้ง endpoint 500 — **ถ้า reuse ให้ระวังเคสหารศูนย์แบบเดียวกัน**

## ตัวเลือกที่ต้องตัดสินใจ (ถาม user ทีละข้อ)

1. **เกณฑ์ "ถูกทาง"** — กำไร > 0 ตอนครบกำหนดพอไหม หรือต้องเกินเกณฑ์ขั้นต่ำ (เช่น > 0.5% ไม่งั้นถือว่าเสมอ)? ทิศทางถูกแต่ขนาดนิดเดียวควรนับเต็มไหม
2. **จุดตรวจเก็บยังไงทั้งที่ไม่มี scheduler** — (ก) คำนวณย้อนหลังจากราคาประวัติศาสตร์ตอนมีคนเปิดหน้า (ข) เก็บ snapshot ทุกครั้งที่มีคนเปิดแล้วยอมรับว่าอาจขาดช่วง (ค) ต้องมี background job จริง — ความเห็นตั้งต้น: **(ก)** เพราะราคาย้อนหลังดึงได้จาก yfinance อยู่แล้ว ทำให้ผลนิ่งและไม่ขึ้นกับว่าใครเปิดแอปเมื่อไหร่
3. **การครบกำหนดใครตัดสิน** — ระบบตัดสินเองตอนคำนวณ (ไม่ต้องมีคนกด) หรือให้ user กดยืนยัน? ต้นฉบับมีปุ่มปิดสัญญาณแบบ admin-only (เห็นคีย์ `prefSignalClose`) แต่นั่นน่าจะเป็นของ tab อื่น — ให้ ticket 01 ยืนยัน
4. **เลยกำหนดแล้วราคาดึงไม่ได้** — สินทรัพย์ที่ yfinance ไม่มี หรือ FRED ยังไม่อัปเดต จะตัดสินยังไง (ห้ามเดาราคา — ต้องแสดง "—" ตามหลักโปรเจค)
5. **ระยะเวลาครบกำหนดมาจากไหน** — AI กำหนดเองตอนออกมติ หรือเราตั้งค่าคงที่ (เช่น 7 วันเสมอ)? ถ้า AI กำหนดเอง มันอาจตั้ง 6 เดือนซึ่งวัดผลไม่ได้ในทางปฏิบัติ — ต้องมีเพดานไหม
6. **สถิติตอนข้อมูลน้อย** — กี่สัญญาณที่สรุปแล้วถึงจะเริ่มแสดงอัตราถูกทาง? ก่อนถึงจำนวนนั้นแสดงอะไร (ต้องไม่ใช่ 100% จาก 1 ตัวอย่าง)
7. **จุดยืนขัดกันข้ามมติ** (จากหมอกในแผน) — แทนที่ / เก็บทั้งคู่ / ปิดอันเก่าอัตโนมัติแล้วนับผล

## Answer

Grilling ครบ 7 ข้อ (2026-08-10) — user ยืนยันทุกข้อ — นิยาม "ถูกทาง" + กลไกจุดตรวจ + กติกาครบกำหนด พร้อมเขียนโค้ดใน ticket 04

### 1. เกณฑ์ "ถูกทาง" (สูตรต้นฉบับ $p — ไม่มี correct flag คำนวณจากราคา)
```
score = (ราคาตอนครบกำหนด − ราคาเข้า) × ทิศทาง   (หน่วยตามกลุ่ม: % / bp / จุด yield)
push_line = (bp ? 4 : 0.5) × √(max(1, horizon_days)/3)
win = score > push_line · loss = score < −push_line · push = |score| ≤ push_line
```
- "ถูกทาง" ต้อง**เกินเส้นขั้นต่ำ** — ทิศทางถูกแต่ขยับนิดเดียว = เสมอ (ไม่เข้าอัตราถูกทาง)
- อัตราถูกทาง = wins/(wins+losses) — push ไม่เข้าตัวหาร

### 2. จุดตรวจ — คำนวณย้อนหลัง on-read (ตัวเลือก ก)
- ราคาเป้า = close ของวันซื้อขายล่าสุด ≤ (ended_at + N วัน) — N = 1/3/7 + horizon_days
- ยังไม่ถึง/ข้อมูลไม่พอ → "ยังไม่ถึงเวลา" (brSigChecksNone) · deterministic ไม่มี storage ไม่มี scheduler
- ใช้ชุดข้อมูลเดียวกับ P&L สด (market_prices candles + macro_history fallback) — price_at อ้างจาก meeting.snapshot

### 3. ครบกำหนด — ระบบตัดสินเอง 100% (ไม่มีปุ่มมนุษย์)
- due_at = ended_at + horizon_days · ถึงเป้า+ข้อมูลพอ → สรุปอัตโนมัติ · ยังไม่ถึง → นับถอยหลัง · ถึงแต่ดึงไม่ได้ → รอสรุปผล

### 4. เลยกำหนดแล้วราคาดึงไม่ได้ — แยก 2 กรณี (ไม่เดา)
- (ก) แหล่งมีแต่ข้อมูลยังไม่ถึงวันเป้า → "รอสรุปผล" (amber) — สรุปเองเมื่อข้อมูลมา
- (ข) สินทรัพย์ไม่มีแหล่งราคาเลย → "ตรวจไม่ได้ — ไม่มีราคา" (เทา) — "—" ทุกช่อง — ไม่นับสถิติ
- ทั้งคู่ไม่เข้าตัวหาร win rate · ไม่มีกำหนดตัดทิ้ง

### 5. ระยะเวลาครบกำหนด — AI ตั้ง + เพดานยาง
- due_at = ended_at + horizon_days (horizon_days จากมติ) · **clamp 1–90 วัน** — เกิน 90 → 90 + บันทึก "ถูกจำกัดที่ 90 (ตั้งไว้ N)" ใน reason · 0/ติดลบ → 1

### 6. สถิติตอนข้อมูลน้อย (mirror boardroom 05)
- settled < 10 → "—" + "รอข้อมูลเพิ่ม (n=N)" · 10–49 → % + เศษส่วนเสมอ · ≥ 50 → % + เศษส่วน
- ใช้กับ: อัตราถูกทาง (หัวการ์ด + รายสินทรัพย์) + สรุปจุดตรวจ (judged < 10 → รอข้อมูลเพิ่ม)
- P&L เฉลี่ยแสดงตั้งแต่ n ≥ 1 **พร้อม (n) เสมอ** · ห้าม 100% เมื่อ n < 10

### 7. จุดยืนขัดกันข้ามมติ — เก็บทั้งคู่ วัดผลอิสระ (ตามต้นฉบับ)
- ทุก stance = สัญญาณแยก (key meetingId:index) · การ์ดโชว์วันที่ประชุมจบ + สินทรัพย์ — ผู้อ่านเห็นความขัดแย้งเอง · track record = ภาพรวม W/L ("ไว้เรียนรู้") · ไม่ทำ filter "มติล่าสุด" (backlog)

**ส่งต่อ:** ticket 04 ได้นิยามครบ (win/loss/push + on-read settlement + due_at = ended_at+horizon_days clamp 90 + cold-start disclosure + เก็บทั้งคู่)
