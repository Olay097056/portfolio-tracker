# 04 - Grilling: เฟส "ตรวจสอบ" — พิสูจน์ข้อกล่าวอ้างด้วยอะไร

Type: grilling
Status: closed
Claimed: hermes/2026-08-09
Blocked by: 01

## Question

เมื่อที่นั่งหนึ่งพูดว่า "HY spread กว้างขึ้น 80bp ในสองสัปดาห์" ระบบจะ**พิสูจน์**ยังไงว่าจริงหรือมั่ว แล้วติดป้าย ผ่านการพิสูจน์ / ขัดกับข้อมูลจริง / ตรวจไม่ได้ ตามเกณฑ์อะไร?

นี่คือหัวใจของทั้งฟีเจอร์ คำโปรยต้นฉบับพูดชัด: *"ยอมรับเฉพาะข้อสรุปที่ผ่านการพิสูจน์ด้วยหลักฐาน"* — ถ้าเฟสนี้อ่อน ที่เหลือก็เป็นแค่ AI คุยกันเล่น

## ข้อเท็จจริงตั้งต้น (ตรวจแล้ว — ข้อมูลที่เรามีให้ตรวจสอบได้จริง)

- `macro_service.build_dashboard()` — ซีรีส์มหภาคทั้งชุด แต่ละการ์ดมี `value`, `change_val`, `change_pct`, `recorded_at`, `available`
- `model_service.build_models()` — คะแนน 6 โมเดล + 5 factor + conditions รายตัว
- `model_score_history` — คะแนนย้อนหลัง (1,794 แถว ณ 2026-08-09)
- `news_items` — ข่าว 7 วันย้อนหลังพร้อม `impact_score`, `related_models`, `published_at`
- `screener_stocks` (986 แถว), `technical_signals` (509 แถว), ราคาผ่าน yfinance
- `countries_service` — yield curve 27 ประเทศ

แปลว่า**ข้อกล่าวอ้างเกี่ยวกับตัวเลขที่อยู่ในชุดข้างบนตรวจได้จริง** ส่วนข้อกล่าวอ้างเชิงตีความ ("เฟดกำลังจะเปลี่ยนท่าที") ตรวจไม่ได้ตามนิยาม

## ตัวเลือกที่ต้องตัดสินใจ (ถาม user ทีละข้อ)

1. **ใครสกัดข้อกล่าวอ้าง** — ให้ที่นั่งพูดออกมาเป็น JSON มีโครงสร้างตั้งแต่แรก (`{claim, metric, expected_value, window}`) หรือให้อีกคอลหนึ่งอ่านบทสนทนาแล้วสกัดออกมา? แบบแรกถูกกว่าและแม่นกว่า แบบหลังเป็นธรรมชาติกว่าแต่เพิ่มคอล
2. **ตรวจด้วยโค้ดหรือด้วย LLM** — ถ้าข้อกล่าวอ้างมีโครงสร้าง โค้ดตรวจได้ตรงๆ (ถูก แม่น ทำซ้ำได้) ถ้าเป็นภาษาธรรมชาติต้องใช้ LLM (แพง และตัวตรวจก็มั่วได้เอง) — ความเห็นตั้งต้น: **บังคับโครงสร้าง แล้วตรวจด้วยโค้ด**
3. **เกณฑ์ผ่าน/ไม่ผ่าน** — ตัวเลขต้องตรงแค่ไหนถึงนับว่า "ผ่าน" (±5%? ±1 s.d.?) ทิศทางถูกแต่ขนาดผิดนับเป็นอะไร
4. **"ตรวจไม่ได้" ต้องแยกเป็นสองแบบไหม** — (ก) ข้อมูลเราไม่มี (ข) เป็นความเห็นไม่ใช่ข้อเท็จจริง — สองอย่างนี้ผู้ใช้ควรเห็นต่างกันไหม
5. **ข้อกล่าวอ้างที่ไม่ผ่านแล้วไง** — ตกไปจากมติเลย (ตามคำโปรยต้นฉบับ) หรือยังแสดงพร้อมป้ายแดง? กระทบสถิติรายที่นั่งยังไง
6. **ที่นั่งแต่งตัวเลขขึ้นมาลอยๆ** — เกิดแน่ ระบบตอบสนองยังไง: ตัดทิ้งเงียบ / แสดงให้เห็นว่าโดนจับได้ / หักคะแนนที่นั่งนั้น

## Answer

Grilling ครบ 6 ข้อ (2026-08-09) — user ยืนยันทุกข้อ — schema ข้อกล่าวอ้าง + กลไกตรวจ + เกณฑ์ตัดสิน พร้อมเขียนโค้ดใน ticket 06

### 1. ใครสกัดข้อกล่าวอ้าง — โครงสร้างตั้งแต่แรก (ตัวเลือก ก)
ที่นั่ง output claims เป็น JSON ต่อท้ายข้อความ → ระบบตัดออกก่อนแสดง + parse เก็บ (ตรงกับต้นฉบับ — ฟังก์ชันตัด `{"claims"` ท้ายข้อความ) — ไม่จ้าง LLM มาสกัดทีหลัง

```json
{"claim": "HY spread กว้างขึ้น 80bp ในสองสัปดาห์",
 "metric": "us_hy_spread",
 "expected": {"value": 80, "unit": "bps", "window_days": 14, "direction": "up"}}
```

- `metric` ต้องเป็น series_id จริงในระบบ (macro/model/model_score_history/news/screener/countries) — ไม่อยู่ใน whitelist → "ตรวจไม่ได้ (ไม่มีข้อมูล)" ทันที
- ขอทีละ 1–3 ข้อ/ข้อความ ไม่ใช่ 10

### 2. ตรวจด้วยโค้ด (ตั้งต้น ticket) — LLM ตรวจเฉพาะตรรกะ
- อ้างตัวเลข/ทิศทางราย series → **โค้ดล้วน** (เทียบจาก snapshot ณ เวลาประชุม)
- อ้าง "ไม่มี/ไม่พบ" → โค้ดเช็ค `available`
- เชิงตีความ (`metric: null`) → ไม่ตรวจ — "ตรวจไม่ได้ (ความเห็น)"
- **whitelist series + คำอธิบาย** ให้โมเดลเลือกจากรายการเท่านั้น (กันส่ง metric มั่ว)
- ผลตรวจระบุชื่อที่นั่งผู้กล่าวอ้าง

### 3. เกณฑ์ผ่าน/ไม่ผ่าน (4 ประเภท) + verdict partial
| ประเภท | match | mismatch | unverifiable |
|---|---|---|---|
| ระดับ | ≤±2% rel (floor ±0.02) | >±5% | ไม่มีค่าปัจจุบัน |
| เปลี่ยนแปลง | ≤±20% ของขนาดอ้าง (floor ±5bp/±0.05%) | >±50% | history ไม่พอ window |
| ทิศทาง | ตรง trend จริง | สวน | ค่าไม่ขยับ |
| คะแนนโมเดล | ตรง ±1 จุด | ต่าง >3 จุด | — |

**verdict 4 ค่า:** ✅ ผ่านการพิสูจน์ · 🔶 **ทิศทางถูก แต่ขนาดคลาดเคลื่อน** (partial — ใช้ในมติเฉพาะทิศทาง ไม่ใช้ตัวเลข) · ❌ ขัดกับข้อมูลจริง · ❔ ตรวจไม่ได้
ตัวเลขอ้างอิง = **snapshot ณ เวลาเปิดประชุม** (กัน "เดาแม่นเพราะเห็นอนาคต")

### 4. "ตรวจไม่ได้" แยก 2 แบบเฉพาะ UI (verdict เดียวในตรรกะ)
❔ **ตรวจไม่ได้ — ไม่มีข้อมูล** · 💭 **ตรวจไม่ได้ — ความเห็น** — badge ต่างกัน, สถิติ/มติ/consensus ใช้ `unverifiable` ค่าเดียว (เป็นกลาง ไม่หักคะแนน)

### 5. ข้อกล่าวอ้างไม่ผ่าน → แสดง + ตกจากมติ + หักสถิติ
- แสดงครบใน transcript พร้อมป้ายสี (เขียว/เหลือง/แดง/เทา) — **ไม่ซ่อน ไม่ตัดทิ้งเงียบ**
- มติ: failed + partial(ตัวเลข) ตก — CEO ใช้เฉพาะ verified + ทิศทางของ partial (brByJames: "จากข้อสรุปที่ผ่านการพิสูจน์เท่านั้น")
- สถิติที่นั่ง: `claims_total/verified/partial/failed` — อัตราหลัก = verified/total · failed+partial หักคะแนน · unverifiable เป็นกลาง
- failed ≥ 3 ข้อ/ประชุม → CEO note "ลดน้ำหนักมุมมองที่นั่งนี้"

### 6. นโยบาย 3 ชั้นกันแต่งตัวเลข
1. **ป้องกัน**: กติกา prompt + whitelist + "(สมมติ)" กำกับฉากทัศน์ (ฟรี)
2. **จับได้**: โค้ดตรวจ → ป้ายแดง + ระบุชื่อที่นั่ง ("อ้าง 80bp จริง 4bp") — โดนจับต่อหน้าห้อง
3. **ลงโทษ**: หักสถิติ + CEO note + ระยะยาว accuracy <45% ฐาน ≥50 ครั้ง → ป้าย advisory (กลไกต้นฉบับ)

ไม่ทำ: ตัดทิ้งเงียบ · หยุดประชุมกลางคัน · hard-ban — ประชุมเดินต่อ ระบบไม่พังเพราะคนโกง 1 คน

**ส่งต่อ:** ticket 06 ได้ schema claims + ตัวตรวจโค้ด (เกณฑ์ 4 แบบ + partial) + นโยบายลงโทษ — ticket 05 ได้นิยาม "สิ่งที่ผ่านการพิสูจน์" สำหรับสมองส่วนกลาง

**ห้ามแตะโค้ด production**
