# Dashboard UI Redesign (wethaiinvest.com-inspired layout)

## Problem Statement

The Dashboard page is functionally complete (ticker/range selection, auto and manual support/resistance zones, drag-to-reposition) but visually it's still bare, unstyled HTML — a `<select>`, a `<select>`, a chart, four plain buttons, and a plain `<table>`, none of it wrapped in the card system the "UI theme foundation" ticket just introduced. On top of that, the price chart itself has never had its own colors set, so it renders as a plain white rectangle sitting inside an otherwise near-black page — a pre-existing visual defect, not something introduced by this ticket, but one this ticket is the natural place to fix since it's re-touching the same component. I want the Dashboard to look and feel closer to wethaiinvest.com's own price-chart dashboard (which I inspected directly, logged in, earlier in this project) — card-wrapped panels, a prominent price + change readout, a button-row range selector, and zone-kind color-coding carried consistently from the chart into the buttons and the zone list — without touching any of the interaction logic (auto/manual zones, freeze semantics, drag mechanics) that already works and was already reviewed.

## Solution

Wrap the Dashboard's existing content in two cards using the `--card-*` tokens from the theme foundation ticket: one card holding the ticker selector, a new price + change readout, a range button-row (replacing the current range `<select>`), the chart itself, and the S/R/Freestyle/Recompute-defaults button row (now color-coded by zone kind); a second, separate card holding the zone list (now with color-coded kind badges). The chart's own background/text/grid colors are set for the first time, resolved at runtime from the same CSS custom properties everything else uses, so it stops being a white rectangle. A loading indicator is added wherever a zone mutation is in flight, replacing the current bare `disabled` state with something visibly communicating "working." No selection logic, zone-freeze semantics, drag mechanics, or backend contract changes at all — this is a pure presentation-layer pass over already-working functionality.

## User Stories

1. As the app's single user, I want the Dashboard's controls and chart wrapped in a card matching the app's new theme, so that the page looks intentional instead of bare HTML sitting directly on the page background.
2. As the app's single user, I want the zone list in its own separate card below the chart card, so that it reads as its own distinct section rather than blending into the chart panel.
3. As the app's single user, I want to see the selected ticker's current price and today's change (colored red for a loss, the new green for a gain) prominently above the chart, so that I don't have to visually parse the chart itself just to know where the price is right now.
4. As the app's single user, I want the range selector to be a row of buttons (1D/5D/1M/6M/YTD/1Y/5Y) instead of a dropdown, so that switching ranges is a single click instead of opening a dropdown first.
5. As the app's single user, I want the currently-selected range button visibly highlighted, so that I always know which range I'm looking at without reading the button labels.
6. As the app's single user, I want the S, R, and Freestyle buttons colored to match their zone's color on the chart (teal, amber, violet), so that I can tell at a glance what each button will draw without reading its label every time.
7. As the app's single user, I want the "Recompute defaults" button visually distinct from the other three (since it's a destructive, confirmation-gated action), so that I don't confuse it with an ordinary add-zone button.
8. As the app's single user, I want the zone list's "kind" column to show the same color-coded badge as the buttons and chart lines, so that scanning the list for, say, all my support zones doesn't require reading every row's text.
9. As the app's single user, I want some visible feedback (not just a grayed-out button) while a zone add/edit/delete/drag commit is in flight, so that I know the app is working rather than wondering if my click registered.
10. As the app's single user, I want the chart itself to have a dark background and light grid/text lines matching the rest of the page, so that it no longer looks like a broken white box embedded in a dark app.
11. As the app's single user, I want the chart's colors to be derived from the same theme tokens the rest of the page uses (not duplicated hardcoded values), so that a future theme change doesn't require remembering to also update the chart component separately.
12. As the app's single user, I want none of this visual work to change how zones are added, edited, deleted, dragged, frozen, or recomputed, so that the already-reviewed and merged interaction logic isn't put at risk by a purely cosmetic ticket.
13. As the app's single user, I want the ticker dropdown to keep working exactly as it does today (just restyled to match the new theme, not replaced with an autocomplete search), so that this ticket doesn't grow into rebuilding ticker selection.

## Implementation Decisions

**Scope boundary — visual/layout only:** this ticket touches `DashboardPage.tsx`, `PriceChart.tsx`, and `ZoneList.tsx` for presentation only. It does not modify `useChartData.ts`, `useZoneEditing.ts`, `client.ts`, `types.ts`, or any backend file — none of the auto/manual zone logic, freeze semantics, busy-guard, or drag-commit behavior changes. The reference site's explicit three-way "Move Chart / Add Support/Resistance / Clear All" interaction-mode toggle (which sidesteps the drag-vs-pan conflict noted as a residual finding on the prior drag-zones ticket) was considered and explicitly deferred — not adopted here, and not decided against permanently; it remains a candidate for a future, separate interaction-focused ticket if wanted.

**Card structure:** two separate card containers, using the `--card-bg`/`--card-radius-lg`/`--card-shadow` tokens from the theme foundation ticket:
- **Chart card**: ticker `<select>` (restyled, not replaced), the new price+change readout, the range button row, the `PriceChart` component, and the S/R/Freestyle/Recompute-defaults button row — all inside one card, since they operate together as a single interactive unit.
- **Zone list card**: the `ZoneList` table alone, in its own card below the chart card.

**Price + change readout:** computed client-side from the existing `points` array already returned by `useChartData` — no backend or API-contract change. The latest point's `close` is the current price (already used today as `currentPrice` for the S/R/Freestyle buttons); the change is `latest.close - previous.close`, and the change percent is that delta divided by the previous close. When `points` has fewer than 2 entries (loading, error, or a single-point range), the readout is omitted rather than shown with a fabricated or zero change — consistent with this project's standing "never fabricate" principle. Positive change renders in `--green`; negative in `--red`; the two Dashboard tickets that came before this one already established the `--red`/`--green` tokens as the app's sole gain/loss color vocabulary, and this readout reuses them rather than introducing a third convention.

**Range selector:** the existing `<select id="dashboard-range">` is replaced with a row of seven buttons, one per `ChartRange` value, in the same order the `RANGES` array already defines. The button matching the current `range` state is visually distinguished (background or border in `--primary`) from the other six. This changes `DashboardPage.tsx`'s DOM structure for range selection — tests that currently locate the range control via `getByLabelText(/range/i)` need to be re-pointed at the new button group (e.g. `getByRole('button', { name: /1 year/i })` or similar, matching the existing accessible-name convention already used for the S/R/Freestyle/Recompute buttons in this file's tests).

**Ticker selector:** left as a `<select>` — only its visual styling (border, background, font) changes to match the new theme tokens. No autocomplete, no new component, no behavior change. Explicitly out of scope per user decision during grilling.

**Zone-kind color coding, reused everywhere:** the three colors already defined in `PriceChart.tsx` for zone rendering (`SUPPORT_COLOR` teal `#14b8a6`, `RESISTANCE_COLOR` amber `#f59e0b`, `FREESTYLE_COLOR` violet `#8b5cf6`) become the single source of truth for zone-kind color everywhere a zone kind is shown in the UI — the S/R/Freestyle buttons and the `ZoneList` kind-column badges both derive their color from the same three values (extracted to a shared, exported constant/lookup so `PriceChart.tsx`, `DashboardPage.tsx`, and `ZoneList.tsx` cannot drift apart, rather than each file defining its own copy of the same three hex values). "Recompute defaults" is not a zone kind and gets its own distinct treatment — a warning-toned outline/border (using `--red` at reduced opacity, consistent with this app's existing convention of using `--red` to signal a destructive/risky action) rather than a fill color, since it doesn't correspond to any zone color.

**Busy/loading indicator:** wherever `zoneEditing.busy` is currently used only to set `disabled`, this ticket adds a visible loading affordance alongside it — a small inline spinner (a lightweight CSS-only spinner, no new dependency) shown next to the busy control, or an opacity/cursor change plus spinner on the affected button(s). Exact placement is an implementation detail for the plan, not a further grilled decision — the requirement is only that "busy" is visibly communicated beyond the native disabled-button graying that exists today.

**Chart colors — the pre-existing white-background defect fix:** `PriceChart.tsx`'s `createChart()` call currently passes no `layout` option at all, so `lightweight-charts` renders its own default white background with dark gridlines/text — clashing with the dark theme every other Dashboard ticket has shipped against. This ticket adds a `layout` option resolving `background.color`, `textColor`, and grid line colors from the same CSS custom properties the rest of the app uses (`--card-bg`, `--text`, and a subtle grid-line color — `--border` is the existing token whose semantic purpose, an unobtrusive divider color, fits grid lines best). Because `lightweight-charts` draws to a `<canvas>`, and a `<canvas>` 2D context's fill/stroke colors must be literal resolved color strings — a raw `"var(--card-bg)"` string is not resolved by the Canvas API the way it would be in a CSS property — these values are read via `getComputedStyle(document.documentElement).getPropertyValue('--card-bg')` (and the equivalent for the other two tokens) at chart-creation time, not hardcoded as a second copy of the hex values already defined in `theme.css`. This keeps `theme.css` as the single source of truth: a future palette change requires editing only that file.

## Testing Decisions

Tests continue to assert observable behavior through the same seams already used throughout this codebase's Dashboard test suite — `DashboardPage.test.tsx` (RTL, querying by role/label text), `PriceChart.test.tsx` (RTL plus the existing `vi.mock('lightweight-charts', ...)` pattern, asserting on calls made into the mocked `createChart`/`addSeries`/`createPriceLine` functions), and `ZoneList.test.tsx` (RTL). No new test files or new testing seams — this ticket extends the three existing ones.

- **Price + change readout:** unit-level assertions in `DashboardPage.test.tsx` covering the computed value from a 2+ point `points` array, and confirming the readout is absent (not zero, not fabricated) when `points` has 0 or 1 entries.
- **Range button row:** `DashboardPage.test.tsx` tests currently driving range changes via `fireEvent.change(getByLabelText(/range/i), ...)` are rewritten to `fireEvent.click` on the corresponding button; a new test asserts the currently-selected range's button is visually distinguished (e.g. an `aria-pressed="true"` attribute or a distinguishing class — whichever the plan settles on — checked via RTL, not by asserting on raw CSS/computed style, matching this codebase's existing preference for asserting behavior over implementation).
- **Zone-kind color reuse:** a test (likely in `PriceChart.test.tsx`, extended, since that's where the color constants already live and are already tested) confirming the S/R/Freestyle buttons and the `ZoneList` badges both resolve to the same three colors already asserted against `createPriceLine` calls — proving the "single source of truth" decision above actually holds, not just that each surface independently picked the right-looking value.
- **Busy indicator:** extends the existing "disables the S/R/Freestyle/Recompute buttons while a zone mutation is in flight" test in `DashboardPage.test.tsx` to also assert the new loading affordance is present during that window and gone afterward.
- **Chart color resolution:** a `PriceChart.test.tsx` test mocking `getComputedStyle` (or setting the relevant CSS custom properties on `document.documentElement` directly in the test, whichever proves simpler against jsdom) and asserting `createChart` is called with a `layout` option containing the resolved (not literal `var(...)`) color strings.
- No visual regression / screenshot testing is introduced — this codebase has none today, and adding one is out of scope for this ticket.

## Out of Scope

- Any change to zone add/edit/delete/drag/freeze/recompute logic, `useChartData.ts`, `useZoneEditing.ts`, the API client, or any backend file.
- The reference site's explicit "Move Chart / Add Support/Resistance / Clear All" interaction-mode toggle — deferred, not decided against, candidate for a future ticket.
- Ticker selection redesign (autocomplete/search) — the `<select>` stays, restyled only.
- Card-wrapping any other page (Portfolios, Watchlist, Tools) — each gets its own future ticket per the sequence agreed in the theme foundation ticket's grilling.
- Chart type toggle (candlestick/Heikin Ashi), overlay controls (Bollinger Bands, trend lines), frequency selector (minute/day/week/month), or the reference's "lock S/R lines" toggle — none of these exist in this app today and none are added by this ticket.
- Visual regression/screenshot test tooling.
- Any reproduction of the reference site's AI-generated analysis content, admin-curated feeds, or other non-visual features — unaffected, already out of scope per `PRD.md`.

## Further Notes

- This is the second ticket of the multi-ticket wethaiinvest.com-inspired UI effort; the theme foundation ticket (`docs/specs/2026-08-04-ui-theme-foundation.md`) landed first and defined the `--card-*` tokens this ticket is the first to actually consume. The remaining pages in the agreed sequence — Portfolios, Watchlist, Tools — each get their own spec and grilling round after this one merges.
- The chart's white-background defect predates this ticket (present since the very first Dashboard walking-skeleton ticket) but is fixed here because this ticket is already re-touching `PriceChart.tsx`'s `createChart()` call site for the theme-color work, making this the natural, lowest-cost point to fix it rather than opening a separate ticket for a one-line-cause defect.
- The zone-kind-color single-source-of-truth extraction (shared constant consumed by `PriceChart.tsx`, `DashboardPage.tsx`, and `ZoneList.tsx`) is a small prefactor this ticket's plan should do early, before the button/badge work depends on it — "make the change easy, then make the easy change."
